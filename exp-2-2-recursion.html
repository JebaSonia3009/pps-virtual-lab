Recursion and the Call Stack

Unit 2 · Modularity · Estimated time: 60 minutes

Aim

To understand how a recursive function solves a problem by calling itself on a smaller subproblem, and to observe the call stack expanding until the base case is reached and then contracting as values are returned.

Learning outcomes

After completing this experiment, a student will be able to:

  1. Identify the base case and the recursive case of a recursive function and explain why both are essential.
  2. Trace a recursive call, stating the value of the parameter in every frame on the stack.
  3. Explain that nothing is computed on the way down: the pending calls wait, and the answer is assembled on the way back up.
  4. Write a valid recurrence relation for problems such as factorial, digit counting, GCD and power.
  5. Explain what causes a stack overflow and how a missing or unreachable base case produces one.
  6. Count the number of calls made and the maximum stack depth, and use these to compare recursive solutions.

Prerequisites

Experiment 2.1 — functions, the call stack and pointers.

Theory

A recursive function is one that calls itself. It is not a special language feature: every call creates its own stack frame in the ordinary way, so a function calling itself simply produces several frames of the same function, each with its own parameters and local variables.

The two parts of every recursive function

A correct recursive function has exactly two kinds of case:

  • The base case — a version of the problem small enough to answer immediately, with no further call.
  • The recursive case — which does a little work and then calls itself on a strictly smaller subproblem.

Both are required. Without a base case the calls never stop. And the subproblem must actually move towards the base case: fact(n) calling fact(n) would recurse forever even though a base case exists, because the argument never shrinks.

Down, then up

This is the part that most often confuses beginners. When fact(4) is evaluated, almost nothing is computed on the way down. Each call reaches the line return n * fact(n - 1);, finds that it cannot multiply yet because the right-hand operand is unknown, and suspends. A new frame is created and the old one waits.

So the stack grows: fact(4), fact(3), fact(2), fact(1). Only when the base case returns 1 does anything get multiplied. The values are then combined on the way back up, each suspended frame resuming, completing its multiplication and returning in turn.

going down                    coming back up
fact(4) = 4 * fact(3)  …waits      … = 4 * 6  = 24
fact(3) = 3 * fact(2)  …waits      … = 3 * 2  = 6
fact(2) = 2 * fact(1)  …waits      … = 2 * 1  = 2
fact(1) = 1            base case   returns 1

Recurrence relations

ProblemBase caseRecursive case
Factorialfact(0) = 1fact(n) = n × fact(n−1)
Count digitscount(n) = 1 when n < 10count(n) = 1 + count(n / 10)
GCD (Euclid)gcd(a, 0) = agcd(a, b) = gcd(b, a % b)
Powerpower(a, 0) = 1power(a, n) = a × power(a, n−1)
Fibonaccifib(0) = 0, fib(1) = 1fib(n) = fib(n−1) + fib(n−2)

The cost of recursion

Every pending call occupies a frame, so the memory used grows with the depth of the recursion. A recursion 10 deep is harmless; one 100,000 deep exhausts the space the operating system reserves for the stack, and the program is terminated with a stack overflow. A missing base case reaches this within a fraction of a second.

Linear and tree recursion

Factorial makes one call per level, so n calls in total and a maximum depth of n. Fibonacci makes two calls per level, so the number of calls grows exponentially while the depth stays around n. Computing fib(20) naively takes over thirteen thousand calls, most of them recomputing values already worked out elsewhere. The Demo counts the calls so this can be seen rather than taken on trust.

Depth and call count are therefore two separate costs, and a recursive solution can be cheap in one and expensive in the other.

Procedure

Step 1

Read the Theory and attempt the Pretest. Note your score.

Step 2

Open the Demo, select Factorial with n = 4, and step through. Watch the stack grow four frames deep. Note that each waiting frame shows the multiplication it is suspended on.

Step 3

Keep stepping past the base case. Watch the frames disappear one at a time and the returned value being multiplied at each level on the way back up. Confirm that nothing was multiplied before the base case was reached.

Step 4

Select Count the digits and run it for a five-digit number. Note the maximum depth and compare it with the number of digits.

Step 5

Run GCD by Euclid's algorithm for 48 and 18. Note how quickly the arguments shrink, and how few frames are needed compared with the size of the numbers.

Step 6

Run Fibonacci for n = 5, then n = 6, then n = 7, and record the call count each time from the statistics bar. Note how fast it grows while the depth barely changes.

Step 7

Run A missing base case and observe what happens. Read the final observation carefully.

Step 8

Open Practice and complete at least eight programs correctly, then attempt the Posttest.
