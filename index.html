Introduction

Beginning programmers can usually write a C program that compiles, yet still be unable to say why it produced the output it did. The gap is that a compiler hides everything interesting: how a value is stored in memory, why 5/2 is 2 and not 2.5, which branch of a decision was actually taken, how the call stack grows and shrinks during recursion, and what happens on the heap when malloc is called.

This virtual lab makes those hidden steps visible. Each experiment pairs a short body of theory with interactive simulations that execute real C programs one step at a time, showing the state of memory and the reason for every decision as it happens. Several programs are provided for each concept, and their values can be changed and re-run, so a student can test whether an idea holds for numbers other than the ones in the textbook. Practice sections then ask the student to predict behaviour and give a hint, rather than the answer, when they are wrong.

Beyond the fifteen experiments, three further labs draw on all five units at once and carry no theory, so that one class can be taught at three speeds from the same link. Guided Programs covers the ground again more slowly for students who need it. The Challenge Lab sets scenario problems for students who finish early. The Placement Lab holds a hundred written-test questions, each with a worked explanation, and fifteen coding problems with the test cases an online judge would use.

The lab complements the physical programming laboratory rather than replacing it. Students still write and compile their own code; the virtual lab explains what the machine did with it. It runs entirely in a web browser, needs no installation and no login, and works on a phone as well as on a desktop computer. Every program on every page has been run and its printed output checked against the program itself, and every answer to every question has been verified the same way.

Objectives

The key objectives of this virtual lab are:

  1. To give students a concrete mental model of memory in C — how values of each data type are stored, how arrays occupy contiguous locations, how the stack holds function calls, and how the heap is managed by hand.
  2. To make the order of evaluation visible, so that operator precedence, associativity, type promotion and short-circuit logic become predictable rather than memorised.
  3. To let students observe control flow directly: the path taken through a decision, the iterations of a loop, and the expansion and contraction of the call stack during recursion.
  4. To support reasoning about cost, by counting iterations, recursive calls and memory used, so that students can compare an iterative and a recursive solution on evidence.
  5. To develop the habit of predicting a program's output before running it, which is the foundation of debugging.
  6. To provide self-assessment through graded pretests and posttests attached to every experiment.
  7. To let one class be taught at more than one speed, by offering the same five units again as guided practice for students who need the ground covered more slowly and as scenario problems for students who finish early.
  8. To prepare students for written placement tests and online coding rounds, by setting questions in the forms those tests actually use — predict the output, find the mistake, judge the cost — each answered with an explanation rather than a mark, and coding problems whose test cases name the case that catches a careless solution.

List of Experiments

Experiments are released as they are completed. Each contains Aim, Theory, Procedure, Pretest, Demo, Practice, Posttest, References and Contributors.

UNIT 1

Decision Making

12 hours
1.1

Data Types, Assignment and Expressions

Size, range and storage of int, float and char. Overflow and truncation. Tracing declarations and assignments. Operator precedence, integer division, type promotion, and variable swapping with and without a temporary variable.

Open
1.2

Decision Making with if…else and Boolean Logic

if, if…else and else-if ladders. Relational and logical operators, short-circuit evaluation and range checks. Classification problems: odd or even, positive or negative, vowel or consonant, leap year, character type and eligibility checks.

Open
1.3

switch and Menu-Driven Programs

Case selection, the effect of a missing break, and a comparison of switch with the else-if ladder. Reading a choice from the user with scanf, the bank menu and triangle classification.

Open
UNIT 2

Modularity

12 hours
2.1

Functions, the Call Stack and Pointers

Breaking a problem into smaller functions. Stack frames created and destroyed as functions are called and return. Pass by value compared with pass by reference, with pointer variables shown as arrows into memory.

Open
2.2

Pointers and Helper Functions

What a pointer holds and what it reaches: a side panel reads out p and *p separately at every step, so the two are never confused. Helper functions that return a value, isPrime written both as a return value and through a pointer, and modular programs for a scorecard and temperature conversion.

Open
2.3

Recursion and the Call Stack

The stack expanding to the base case and contracting as values return, for factorial, digit counting, sum of digits, power, GCD, Fibonacci, reversing a number and palindromes. A trace panel names every call and what it handed back, the calls and the deepest level are counted, and an Explorer lets the student make the calls by hand — down to the base case, then back up one answer at a time.

Open
UNIT 3

Array and String

12 hours
3.1

Arrays and Strings

Arrays drawn as touching boxes with the index above and the real address below, so contiguous storage can be seen rather than taken on trust. The null terminator shown as its own shaded box. strlen, strcpy, strcat, strcmp, strrev, strchr and strstr step by step, pointers walking through an array, why a function can change the caller's array, and recursive solutions for string length, largest element, vowel counting and reverse printing.

Open
3.2

Iteration: while, do…while and for

An iteration table beside every program, with one row per pass showing the test, what each variable was before and after, and what that pass printed. Why do…while always runs its body at least once, shown on the same task written both ways, and why menus and input validation need it. Infinite loops and off-by-one errors next to their corrected versions, and an Explorer that makes the student run the test, body and step by hand in the order the form demands.

Open
3.3

Count-Controlled for Loops and Linear Search

Working out the number of passes before running the loop, and checking it against the iteration table. Stepping up and down by any amount, and the two faults that come from the start, the test and the step disagreeing. Linear search in both the successful and the unsuccessful case, with the comparisons counted, written once with return and once with break. Patterns with nested loops, and the three practice functions: reverse printing, countFrequency and mergeStrings.

Open
UNIT 4

Structured Iterations

12 hours
4.1

Nested Loops, Matrices and Bubble Sort

Tracing a nested loop and counting its iterations, with the growth from n to n squared made visible. Patterns up to a hollow square. A matrix drawn as a grid with every cell's real address, next to the truth that it is one straight row-major block — so m[0][4] landing on m[1][0] becomes obvious rather than mysterious. Row sums, column sums, both diagonals and the sparse-matrix test, including the integer division that makes the obvious version of that test never fire. Bubble sort traced pass by pass with the compared pair highlighted, the comparisons counted against n(n−1)/2, and the swap that loses a value when the temporary is left out.

Open
4.2

Recursion against Iteration: Stack, Calls and Cost

The same problem solved both ways, with the cost measured rather than argued about: frames on the stack, function calls, loop passes and bytes of memory, counted live as the program runs. Factorial and Fibonacci both ways, and why recursive Fibonacci is in a different class of bad from recursive factorial. Binary search recursive and iterative with the calls and the passes printed, including the extra call the recursion needs to discover a failure. Palindrome and power both ways, global call counters drawn apart from the stack, and an Explorer that measures the two approaches side by side at any size.

Open
4.3

break, continue and the Cost of Repetition

What the two jump statements really do, shown by counting: break ends the loop and the passes it skipped never happen, while continue ends only one pass and the loop runs just as many times as before. The mistake that hangs a while loop, caught and explained. Reading values with scanf until a stopping value arrives, with a typed-input box the student can edit, and what happens when that value never comes. Sum of digits written both iteratively and recursively with the intermediate steps counted, and an Explorer that builds a loop from your choices and measures what each one cost.

Open
UNIT 5

Memory Driven Problems

12 hours
5.1

Structures and Arrays of Structures

A record drawn as one block with its members laid side by side, each at a known distance from the start — and the measurement showing that a structure costs no more memory than the same facts kept in separate variables. Arrays of records, with every record exactly one record-length after the last, so list[i] is one multiplication away. A record passed by value appears twice, once in each frame, so the function provably works on a copy; passed by pointer, one record with an arrow reaching it. Functions that take a record and return an updated one, and a search through an array of records that returns either the record or its position — with a program showing why the difference matters.

Open
5.2

Dynamic Memory Allocation

The heap drawn as its own region below the frames, so a block asked for inside a function can be watched staying exactly where it is after that function has returned. Boxes from malloc shown as unwritten until the program fills them, against the zeros calloc gives; realloc both growing a block in place and having to move it, copying as it goes. The three mistakes that follow free — a dangling pointer, a double free and a leak — each with a program that stops and explains itself. Records built on the heap and handed back by a function, a linked list grown and freed one node at a time, and an Explorer that measures three ways of holding values whose number is not known in advance.

Open
5.3

File Handling

The file drawn beside the program with a marker for the read position, so each fscanf or fgets can be watched moving through it — and the file itself is editable, so every count changes with the data. Newlines shown as the characters they are, which is what makes fgets keeping them make sense. The while (!feof(fp)) mistake set next to the correct loop, reporting six values for a file of five. Counting lines, words and characters, beside a word counter that misses the first word of every line. A frequency report as a list, as bars, and written out to a second file with fprintf. An Explorer that reads any text you paste both as lines and as numbers at once.

Open

Practice Labs

Alongside the fifteen experiments, these three labs gather work from all five units in one place and carry no theory. The first covers the ground again more slowly; the second sets problems for students who finish early; the third prepares for written placement tests and online coding rounds. All three are open to everyone, and a student can move between them freely.

Across all five units
P

Guided Programs — Slow Learners

Fifty-four programs covering all five units, the easiest first and rising gently within each unit, with no theory to read. Each program runs a line at a time with the memory picture beside it and the values can be changed. Check yourself asks ten questions per unit, where a wrong answer explains itself and names the program to go back to. Write your own is a C editor that starts with a program already loaded, so a student can begin by changing one number; it reports a missing semicolon in plain words rather than failing silently.

Open
C

Challenge Lab — Fast Learners

Forty problems across the same five units, each written as a situation to work out rather than an instruction to follow: slab tariffs, Euclid's algorithm, the Tower of Hanoi, majority voting, rotation by three reversals, the sieve of Eratosthenes, spiral printing, saddle points, self-doubling arrays, reversing a linked list and finding its middle in one pass. The solution stays hidden until it is asked for, and a hint sits between the two. Each revealed solution carries a note on the trick it turns on and where else that trick applies. The quizzes are about complexity, edge cases and why one approach beats another, and the editor starts blank.

Open
PL

Placement Lab — Written tests and coding rounds

A hundred questions of the kind written tests actually ask — predict the output, find the mistake, judge the cost — twenty per unit, chosen from a drop-down by unit and by kind. A student answers, presses Check, and the explanation appears at once; the questions come in a different order each time, so going round a unit twice is not the same twice. Alongside them sit fifteen coding problems, three per unit, each with a brief, a hint, and the test cases a judge would use — the empty input, the single item, the value exactly on the boundary — with a note against each case saying which careless solution it catches. The worked solution stays hidden until it is asked for, and then runs a line at a time like everything else.

Open

Target Audience

  • First-year undergraduate students of engineering taking an introductory programming course in C, across all branches. The fifteen experiments follow the syllabus unit by unit.
  • Students within the same class who are working at different speeds. Those who need the ground covered again more slowly have Guided Programs; those who finish early have the Challenge Lab. Both are open to everyone and a student may move between them freely, so nobody is labelled by which link they open.
  • Students in any semester preparing for placement. The Placement Lab sets written-test questions with worked explanations and coding problems with test cases, arranged by unit so that revision can follow whichever topic is weakest.
  • Students in higher semesters revising C before a data structures course.
  • Diploma and polytechnic students studying computer programming fundamentals.
  • Teachers who wish to demonstrate memory layout, expression evaluation, recursion, dynamic allocation and file handling live during a classroom lecture, without setting up a compiler.

No prior programming experience is assumed. A student needs only a web browser and an internet connection; the pages work on a phone as well as on a desktop computer.
