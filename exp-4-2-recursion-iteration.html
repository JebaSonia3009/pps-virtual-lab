Recursion against Iteration: Stack, Calls and Cost

Unit 4 · Structured Iterations · 26 programs to explore · Estimated time: 80 minutes

Aim

To solve the same problem both recursively and iteratively, and to measure what each one costs — frames on the stack, function calls, loop passes and bytes of memory — rather than arguing about which is better in the abstract.

Learning outcomes

After completing this experiment, a student will be able to:

  1. Write a recursive and an iterative version of the same function and show that they give the same answer.
  2. Explain what a stack frame costs: its own copy of every parameter and local variable, kept alive until the call returns.
  3. Say why a recursive solution's memory grows with n while an iterative one's does not.
  4. Describe function call overhead — the work of making a call, beyond the memory it uses.
  5. Compare the memory behaviour of recursive and iterative factorial and Fibonacci, and explain why recursive Fibonacci is in a different class of bad from recursive factorial.
  6. Implement binary search both ways, count the recursive calls and the loop passes, and explain why the counts are the same.
  7. Choose between the two forms for a given problem and defend the choice.

Theory

The same answer, different cost

Anything that can be written recursively can be written as a loop, and the other way round. They are equally powerful. So the question is never "which one works" — it is what each one costs, and that is something you can measure.

int fact(int n) {                        int factIter(int n) {
    if (n == 0) return 1;                    int i, f = 1;
    return n * fact(n - 1);                  for (i = 1; i <= n; i = i + 1)
}                                                f = f * i;
                                             return f;
                                         }

What a stack frame costs

Every function call gets a stack frame: its own private space holding its parameters, its local variables, and a note of where to go back to when it finishes. That frame cannot be released while the call is still waiting for an answer.

So in fact(6), at the deepest moment, seven frames exist at once — one for each of 6, 5, 4, 3, 2, 1, 0 — plus main. The loop version keeps one frame, however large n is.

That is the whole memory story in one table: one column grows with n, the other does not. The Demo shows the live byte count beside every program, so this is measured rather than asserted.

Real stacks are finite — typically a few megabytes. A recursion a few thousand levels deep will exhaust it and the program will be killed, an error called a stack overflow. A loop cannot fail that way. This lab stops at 60 frames so you can see the limit arrive safely.

Function call overhead

Memory is not the only cost. Making a call also takes work, every single time:

  • the arguments are worked out and copied into the new frame,
  • the return address is saved,
  • control jumps to the function and later jumps back,
  • the frame is set up and then thrown away.

A loop pass does almost none of that — it tests a condition and changes a counter. That is what call overhead means: not that calls are slow in some mysterious way, but that each one carries this small fixed bundle of work that a loop pass does not. The Demo counts calls and loop passes separately so the two can be compared directly.

Factorial: linear recursion

Recursive factorial makes exactly n + 1 calls and goes n + 1 levels deep. It is wasteful of memory compared with a loop, but only mildly so, and the recursive version reads almost exactly like the mathematical definition. For small n it is a perfectly reasonable choice.

Fibonacci: a different kind of bad

Recursive Fibonacci is not merely wasteful. Each call makes two further calls, so the number of calls grows explosively, and the same small problems are solved again and again:

Note the difference from factorial. Recursive factorial uses more memory than the loop but does the same amount of work. Recursive Fibonacci does an enormously greater amount of work — fib(20) makes over twenty thousand calls where a loop makes nineteen passes. Its stack depth, interestingly, stays modest at about n; it is the number of calls that explodes, not the depth.

So "recursion is slower" is too blunt a statement. Recursive factorial is slower than its loop by a small constant factor. Recursive Fibonacci is slower by a factor that grows without limit. The reason is not recursion itself but repeated work: the same fib(3) is computed over and over because nothing remembers the answer.

Binary search: the fair comparison

Binary search is the honest case, where recursion and iteration cost almost the same. Each step halves the range, so both versions take about log₂n steps:

recursive                                iterative
if (low > high) return -1;               while (low <= high) {
mid = (low + high) / 2;                      mid = (low + high) / 2;
if (a[mid] == key) return mid;               if (a[mid] == key) return mid;
if (a[mid] < key)                            if (a[mid] < key) low = mid + 1;
    return search(a, mid+1, high, key);      else high = mid - 1;
return search(a, low, mid-1, key);       }
                                         return -1;

Because the depth stays so small — twenty frames to search a million items — the recursive version's memory cost is negligible here. This is the case where you may reasonably choose recursion for readability. The Demo prints both counts so you can confirm they match.

One small asymmetry worth noticing. When the key is not present, the recursive version makes one extra call: the call that discovers low > high and returns −1. The iterative version simply finds its condition false and never enters the body again. The Demo shows both counts side by side so students can spot this themselves rather than being told.

Counting with a global

To print how many calls were made, the count has to survive across all of them. A variable declared outside every function does exactly that — it is created before main starts, lives until the program ends, and every function can see it:

int calls = 0;        /* outside every function, so every function shares it */

int fact(int n) {
    calls = calls + 1;
    ...
}

The Demo draws these in a separate dashed block, apart from the stack, because that is exactly what they are: not part of any frame, and not thrown away when a function returns.

Globals are used sparingly in real programs, because anything can change them and it becomes hard to see who did. For counting calls in a teaching program they are the clearest tool; for passing data between functions, parameters and return values are better.

Choosing between them

Prefer recursion whenPrefer a loop when
The problem is defined on a smaller version of itselfThe work is plain repetition
The depth stays small (binary search, tree work)The depth would grow with the data
The recursive version is markedly clearerMemory or speed actually matters

Procedure

  1. Read the Theory, especially the table of frames at once for each n.
  2. Attempt the Pretest before looking anything up.
  3. Open the Demo at Factorial, both ways. Run the recursive version and watch the frames pile up in the memory panel, then the iterative one and watch that it never goes past two. The panel beside it counts frames, calls, loop passes and bytes.
  4. Raise n and watch the recursive byte count rise while the iterative one does not move. Note the exact numbers at n = 4, 8 and 12.
  5. Move to Fibonacci, both ways. Run the recursive version at n = 5, then 8, then 12, and watch the call count rather than the depth. Compare with the loop.
  6. In Binary search, search for a key that is present and note that both counts agree. Then search for one that is absent and find the extra recursive call.
  7. In Palindrome and power, work through both versions of each.
  8. Run A recursion too deep and read what happens when the stack runs out.
  9. Use the Explorer to set n and see the two costs side by side in one table, for each of the four problems.
  10. Work through the Practice section in both modes.
  11. Attempt the Posttest and compare it with your pretest score.
