Dynamic Memory Allocation

Unit 5 · Memory Driven Problems · 42 programs to explore · Estimated time: 90 minutes

Aim

To ask for memory while the program is running, when the amount needed is not known until then — using malloc, calloc, realloc and free — and to build with structures the things a fixed array cannot hold, including a list that grows one record at a time.

Learning outcomes

After completing this experiment, a student will be able to:

  1. Explain why a fixed array is a guess, and what that guess costs when it is too large or too small.
  2. Use malloc to ask for exactly the memory a program needs, and sizeof to work out how many bytes that is.
  3. Check the result of an allocation against NULL before using it, and say what happens if that check is skipped.
  4. State the difference between malloc and calloc, and when the clearing that calloc does is worth paying for.
  5. Use realloc to resize a block at run time, explain why the result must be assigned back, and say what happens to the old block when it moves.
  6. Use free to hand memory back, and recognise the three mistakes that follow it: a dangling pointer, a double free, and a leak.
  7. Describe the difference between the stack and the heap: what each holds, who clears it up, and how long it lasts.
  8. Allocate structures on the heap and reach their members with ->, writing functions that build a record and hand it back.
  9. Build a linked list whose length is decided while the program runs, walk it, search it, and free it correctly.
  10. Compare growth strategies by measurement, and explain why doubling beats adding one.

Theory

The guess a fixed array makes

Every array so far has had its size written into the program: int marks[50];. That works only while you know the number in advance. If 3 students turn up, 47 boxes sit unused. If 80 turn up, the program cannot take them — and C will not stop you from writing past the end, it will simply damage whatever lies beyond.

What is needed is a way to say "give me room for n of these" where n is not known until the program runs. That is dynamic memory allocation, and it needs #include <stdlib.h>.

The stack and the heap

Memory a C program uses comes from two places, and the difference matters more than any syntax on this page.

the stackthe heap
what lives thereparameters and local variables blocks asked for with malloc
how bigfixed when the program is written decided while the program runs
how long it lastsuntil the function returns until free is called
who clears it upthe language, automaticallyyou

That third row is the reason the heap exists. A local array disappears the moment its function returns; a heap block does not. A function can therefore ask for memory, fill it, return a pointer to it, and the memory is still there for the caller — which is exactly what one of the programs in the Demo shows. In the memory picture on this page, the heap is drawn as a separate dashed block below the frames, because it belongs to no frame at all.

malloc: asking for bytes

int *p = (int *)malloc(n * sizeof(int));

Three things are happening. sizeof(int) asks the compiler how many bytes one int needs, so the program never has to assume 4. n * sizeof(int) is therefore the right number of bytes for n of them. And malloc returns the address of a block that big — or NULL if it cannot find one.

About the (int *) in front. malloc returns a void *, which C converts to any object pointer type by itself, so the cast is not required and many authors leave it out. It is written here because that is the form used in most Indian textbooks and examinations, and you should recognise it. Either is correct.

Once you have the pointer, p[0], p[1] and so on work exactly as if p were an array — because, as Unit 2 showed, that is what indexing a pointer has always meant.

Always check for NULL

if (p == NULL) {
    printf("out of memory");
    return 1;
}

Memory can run out. If it does, malloc returns NULL, and using NULL as though it were a block is one of the fastest ways to stop a program dead. Two lines of checking is the whole cost.

malloc does not clear what it gives you

A fresh malloc block holds whatever was in that memory before. Not zero — whatever happened to be there. The Demo shows those boxes as ? until the program writes something, and reading one before writing it gives an answer that can change from run to run.

calloc is the same request with the clearing included:

int *p = (int *)calloc(n, sizeof(int));

Note that it takes two numbers — how many, and how big each one is — where malloc takes one total. Every byte comes back zero. If your next move is a loop that sets everything anyway, malloc is fine; if you are going to count or add things up, calloc saves you a loop and a bug.

realloc: changing your mind

p = (int *)realloc(p, 2 * n * sizeof(int));

realloc resizes a block that already exists, keeping everything already in it. It does one of two things, and which one is not up to you:

  • If there is room immediately after the block, it grows it where it stands and the address does not change.
  • If there is not, it takes a new block elsewhere, copies the old contents across, frees the old one, and returns the new address.

Both happen in the Demo, which is why there are two programs for it. And this is why the result must be assigned back: if the block moved, the old value of p is now a dead address. Any other pointer that was aimed at that block is dangling too, and nothing warns you.

Any new room at the end is not cleared, the same as malloc.

free, and the three mistakes after it

free(p) hands the block back. Notice what it does not do: it does not change p. The pointer still holds the same address, pointing at memory the program no longer owns.

  1. A dangling pointer — using memory after freeing it. C does not catch this. The program may appear to work, may print nonsense, or may stop, and which of those happens can differ between runs. That is the worst kind of bug: one that is not reliably visible.
  2. A double free — freeing the same block twice, which corrupts the memory system's own records.
  3. A leak — never freeing at all. When the program ends the operating system takes everything back, so a small program gets away with it. A program that keeps running does not: it holds more and more until there is nothing left.

One habit prevents the first two:

free(p);
p = NULL;

because free(NULL) is defined to do nothing at all, and if (p == NULL) is now a test you can actually write. The Demo has a program for each of these, including the ones that stop.

Records on the heap

Everything above works for structures too, and this is where the syllabus asks for modular programming using structures:

struct Book *b = (struct Book *)malloc(sizeof(struct Book));
b->code = 21;

Because the record is reached through a pointer, its members are reached with ->, exactly as in Experiment 5.1. What is new is that a function can now build a record and hand it back — the record outlives the function that made it, so a program can be written as small functions that each produce or fill one record. A fixed array of records could never be shared that way.

A list that grows as it goes

Put a pointer to the same kind of record inside the record, and records can be chained together:

struct Node {
    int data;
    struct Node *next;      /* a Node, pointing at another Node */
};

Each node is asked for when it is needed, so the list has no maximum length — it is as long as the data turns out to be. The last node's next is NULL, which is how a walk knows to stop:

walk = head;
while (walk != NULL) {
    printf("%d ", walk->data);
    walk = walk->next;
}

Adding at the front is two lines and the same speed however long the list is; the values then come out in reverse order. Adding at the end keeps the order but needs a pointer to the last node. Both are in the Demo.

Freeing a list has one trap, and it is worth meeting before you write your own:

while (walk != NULL) {
    after = walk->next;     /* save it FIRST */
    free(walk);
    walk = after;
}

Reading walk->next after freeing walk reads memory the program has given away. The Demo has that version too, and the page stops it.

What growing costs

When values arrive one at a time and the total is unknown, there is a real choice to make, and the Explorer measures all three answers. Asking for one more box every time wastes no space but copies the entire collection on every single addition. Doubling the room when it fills up copies far less — for 8 values, 7 copies against 28; for 32 values, 31 against 496 — at the cost of a little room not yet used. The copies made by growing one at a time rise with the square of the number of values; doubling's rise in step with the values. That is why every growable collection in every real library doubles.

Procedure

  1. Answer the Pretest before reading the Theory.
  2. Read the Theory as far as The stack and the heap, and copy that table into your record.
  3. Open the Demo at Why ask at run time. Run the first two programs and compare the bytes each one holds.
  4. Run The heap block outlives the function that asked for it and step through it slowly. Watch the frame for makeRun appear, fill the block, and disappear — while the block itself stays exactly where it was. This is the point of the whole experiment.
  5. Move to malloc, calloc and free. Run the first program, which is the first part of your guided practice. Change n and watch the block change size.
  6. Run malloc does not clear what it gives you and note the boxes shown as ?. Then run calloc clears every byte to zero.
  7. Run calloc, then change only the values that are not zero — the second part of your guided practice.
  8. Run the three programs that stop: using memory after freeing it, freeing twice, and freeing something that never came from malloc. Read each explanation.
  9. Run Forgetting to free: a leak and read the last line of the story.
  10. Open realloc. Run the first program — the third part of your guided practice — then Sometimes realloc has to move the block and Sometimes it does not have to move it, and compare the addresses before and after.
  11. Run Growing one box at a time and Doubling the room instead and write down both copy counts.
  12. Open Records on the heap and run A function that builds a record and hands it back.
  13. Open A list, built as it goes. Run the nodes programs in order. Pay particular attention to Freeing the whole list, the right way and then the wrong way.
  14. Use the Explorer with 8, then 16, then 32 values, and watch the copy counts separate.
  15. Do the Practice questions in both modes until your streak reaches five.
  16. Answer the Posttest.

Guided practice

  1. Allocate memory with malloc for N integers, put values in, compute their sum, and free the memory.
  2. Use calloc to create a zero-filled array, read values into it, and change only the ones that are not zero.
  3. Resize an array with realloc when more elements are added while the program runs.

All three are the first programs of the malloc, calloc and free and realloc tabs. Write each one yourself first, then step through the version here and compare what happens in memory.

Practice

  1. Implement a list using dynamic memory allocation. Build it one node at a time, print it, and free every node. Say in your record whether you added at the front or the end, and why.

The A list, built as it goes tab has both, along with counting, searching and the correct way to free. Write your own before reading them.

Two honest notes on what this page shows. First, the heap here is a simple model:
      blocks are laid out one after another from a fixed address, and a request that cannot be met at the
      top of the block is given a new address. A real allocator reuses freed space, keeps its own records
      between the blocks, and may hand back an address you have seen before — so the exact addresses
      in the picture are illustrative, while the behaviour they illustrate is not. Second,
      realloc here grows a block in place only when nothing has been allocated above it; a
      real implementation may manage it in other cases too, and may equally move a block when this page
      would not. Both behaviours are shown precisely because neither is guaranteed.
