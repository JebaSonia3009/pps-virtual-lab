switch and Menu-Driven Programs

Unit 1 · Decision Making · 17 programs to explore · Estimated time: 60 minutes

Aim

To understand how a switch statement chooses between a fixed set of options, why break is needed, how to read a choice from the user, and when to prefer switch over an if…else if ladder.

Learning outcomes

After completing this experiment, a student will be able to:

  1. Write a switch statement with case labels and a default.
  2. Explain what break does and predict what happens when it is left out.
  3. Use several labels together on purpose so that they share one action.
  4. Read a value from the user with scanf and act on it.
  5. Write a menu-driven program such as a bank menu.
  6. Say which problems suit a switch and which need an if…else if ladder instead.

Prerequisites

Experiment 1.2 — decision making with if…else.

How to use this experiment

The Demo has four concepts. In the programs that use scanf, the box at the top is what the user types — change it and run the program again.

Theory

Some problems offer a fixed list of choices: a menu with four options, a grade letter, a day number. You can write these with an if…else if ladder, but C gives you a statement made for exactly this job — the switch.

The shape of a switch

switch (choice) {
    case 1:
        printf("Deposit");
        break;
    case 2:
        printf("Withdraw");
        break;
    default:
        printf("Invalid choice");
}

The value in the brackets is worked out once. C then looks for a case label with exactly that value and jumps straight to it. If no label matches, it jumps to default. If there is no default either, the whole switch is skipped and nothing happens.

What switch can and cannot test

AllowedNot allowed
A whole number: case 3: A range: case marks >= 75:
A character: case 'A': A float value
A fixed constant known when the program is written A variable as a label: case n:

Two labels in the same switch can never have the same value, and the controlling value must be a whole number or a character — never a float and never a string.

break, and what happens without it

This is the part that surprises everyone the first time. A case label is a place to jump to, not a box with walls around it. Once C has jumped to a label it keeps running straight down the lines below it — through the next label, and the next — until it meets a break or reaches the end of the switch.

So leaving out break in a bank menu means choosing "Withdraw" also runs "Check Balance", "Exit" and the default. Running straight on like this is called fall-through.

Using fall-through on purpose

Fall-through is occasionally exactly what you want. Stacking labels with nothing between them lets several values share one action:

case 'a':
case 'e':
case 'i':
case 'o':
case 'u':
    printf("Vowel");
    break;

Any of those five letters lands on the same printf. This is normal, readable C. The mistake is forgetting a break where you meant to have one.

Reading a value from the user

A menu is only useful if the user can choose. printf writes to the screen and scanf reads what the user types:

int choice;
printf("Enter your choice: ");
scanf("%d", &choice);

The & before the variable name is required. It gives scanf the address of the variable, so it knows where to put what the user typed. Leaving it out is one of the most common beginner's mistakes.

The specifier must match the type: %d for an int, %c for a char, %f for a float.

switch or if…else if?

switchif…else if
TestsIs it equal to this exact value?Any condition at all
RangesCannot do themYes: marks >= 75
TypesWhole numbers and charactersAnything, including float
How it choosesJumps straight to the matching labelTests each condition in turn
Best forMenus and fixed lists of choicesRanges, bands, combined conditions

A four-option menu reads more clearly as a switch. A grade band such as marks >= 75 cannot be written as a switch at all, because a label has to be one exact value.

When both will work, they give the same answer. Choose the one that makes your intention clearer to the next person reading the program.
