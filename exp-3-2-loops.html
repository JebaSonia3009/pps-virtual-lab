Iteration: while, do…while and for

Unit 3 · Array and String · 30 programs to explore · Estimated time: 75 minutes

Aim

To recognise a problem that needs the same work done again and again, express it as a loop, and choose between while, do…while and for with a reason rather than a habit.

Learning outcomes

After completing this experiment, a student will be able to:

  1. Identify a problem that requires repeated computation and write it as a loop.
  2. Name the three parts every loop has — start, test and step — and find them in all three loop forms.
  3. Trace a loop pass by pass in an iteration table, giving the value of every variable at each test.
  4. Explain why do…while runs its body at least once, and convert a while solution into a do…while one and back.
  5. Justify do…while for menu-driven programs and input validation, where the action must happen at least once before there is anything to test.
  6. Recognise and repair an infinite loop and an off-by-one error.
  7. Solve the standard problems: the first N even numbers, the largest of several inputs, and whether a number is a perfect square.

Theory

When a loop is the answer

Some problems ask for the same work to be done over and over: add up 50 marks, print the first 10 even numbers, keep asking until the user types something sensible. Writing the work out 50 times is not an option, and in the third case you do not even know how many times it will be. A loop says the work once and describes when to stop.

Every loop has the same three parts

PartIts jobWhat goes wrong without it
StartSets the variable up before the first pass The variable has no value, so the test is meaningless
TestDecides whether another pass happens The loop never stops
StepMoves the variable towards the test failing The loop never stops — the test is checked but nothing changes

All three forms have all three parts. They differ only in where the parts are written and when the test happens:

int i = 1;                  /* start */        for (i = 1; i <= 5; i = i + 1) {
while (i <= 5) {            /* test  */            printf("%d ", i);
    printf("%d ", i);                           }
    i = i + 1;              /* step  */
}                                               /* all three parts on one line */

In a for loop the three parts are gathered onto one line, which is why for is the natural choice when you know how many passes there will be. In a while loop they are spread out, which suits a loop that stops on a condition rather than a count.

The one real difference: where the test sits

FormOrder of eventsFewest passes possible
whiletest, then body0
forstart, test, body, step0
do…whilebody, then test1

This is the whole of it. A while loop asks permission before doing anything, so if the test is false at the start the body never runs at all. A do…while loop does the work first and asks afterwards, so the body always runs at least once, however false the test is.

int i = 10;                        int i = 10;
while (i <= 5) {                   do {
    printf("ran");                     printf("ran");
    i = i + 1;                         i = i + 1;
}                                  } while (i <= 5);

prints nothing                     prints "ran" once

Mind the semicolon. A do…while loop ends } while (test); — with a semicolon. A while loop written while (test); with a semicolon is a different thing entirely: an empty body, which usually means an infinite loop. Both are shown in the Demo.

Why do…while exists: two real situations

Both of these have the same shape — there is nothing to test until the work has been done once.

SituationWhy the body must run first
A menu The menu has to be shown and a choice read before the program can know whether the user picked "exit". Testing first would mean deciding before asking.
Input validation You cannot check whether a value is sensible until you have read it. The read must come first; the test repeats it only if it was wrong.

Written with a while loop, both force you to duplicate the body: once before the loop and again inside it. That duplication is the sign that do…while was the right form. The Demo shows the same menu written both ways so the duplication is visible.

Reading an iteration table

Beside the memory panel the Demo builds a table with one row per pass. It is the same table you would draw on paper when tracing a loop by hand, and it is the fastest way to see what a loop actually did:

PassTestitotalPrinted
1true1 → 20 → 1
2true2 → 31 → 3
3true3 → 43 → 6
4false46body skipped

Two habits worth building from it. First, the last row is always a test that failed — a loop ends by testing, not by running. A loop that printed three lines has four rows. Second, read the arrow in each cell as "before the pass → after the pass".

For a do…while table the Test column sits on the right, because that is where the test happens — after the body. The table is laid out in the order the events really occur.

The two classic loop bugs

BugWhat it looks likeHow to spot it in the table
Infinite loop The step is missing, or moves the wrong way, so the test never becomes false The variable column never changes from one row to the next
Off by one < written where <= was meant, or a counter started at 0 instead of 1 The table has one row too many or too few — count the true rows

Both are in the Demo on purpose, next to the correct version, so a student can compare the two tables rather than be told the difference.

Choosing between them

If the problem is…Use
"do this exactly N times"for
"keep going while something is true, possibly never"while
"do it, then decide whether to do it again"do…while

Any of the three can be made to do any job. The three forms are equally powerful — the Demo proves it by solving one task three ways. Choosing the one that matches the shape of the problem is about writing code that reads clearly, not about what is possible.

Procedure

  1. Read the Theory, especially the table of which form tests first.
  2. Attempt the Pretest before looking anything up.
  3. Open the Demo at while. Step through the first program and watch the iteration table fill in, one row per pass. Check that the last row is a test that came back false.
  4. Move to do…while. Run The same loop, both ways and When the test is false from the start — the second is the one that matters. Note that the Test column moves to the right-hand side, because the test now happens last.
  5. Run the menu and the input-validation programs, then the while versions of the same tasks, and compare how much had to be written twice.
  6. In for, find the start, test and step on the single for line, and watch the order they run in.
  7. In When loops go wrong, run the infinite loop and the two off-by-one programs. Use the table to find the fault before reading the explanation.
  8. In The three practice problems, work through even numbers, the largest value and the perfect square. Change the values at the top and try the awkward cases: N = 0, equal inputs, and 1.
  9. Use the Explorer to run a loop one event at a time — test, body, step — and build the three forms yourself.
  10. Work through the Practice section in both modes.
  11. Attempt the Posttest and compare it with your pretest score.
